# 搜索候选标识复用对照

2026-09-18，当前源码应用版本 `0.1.0`、算法 `mc-1.6.0`。本记录补充 P2-2 性能证据；既有 `0.3.0 / mc-1.4.0` 验收表属于历史记录。

搜索原先在每个分支中为同一候选配置创建新成员 ID，选出缓存包含成员 ID，因此无法复用这些重复选出。现在每层搜索只创建一组候选成员，各分支共享这些标识；跨层和跨请求仍创建独立标识，保证允许重复物种的自定义规则能够区分每位成员。候选数量、机制、评分、成员顺序、目标、权重和预算规则均未调整。

## 输入与方法

从当前语料依次选择包含灭歌、复活、空间、轻装、喷火龙 Y 和抛下狠话的六支不同真实队伍，各取原队前两位补齐。类别描述来源队伍的机制，不保证前两位或推荐队伍包含该机制。每支分别测量新建 `Evaluator` / `TeamSearch` 的首次请求，以及同实例的重复请求。首次请求仍可能复用进程和模块缓存。

使用默认 48 候选、7 束宽、24 对手代表，不设置墙钟截止；计时包含推荐与解释生成，不包含加载数据和结果断言。每种条件只测一次，不能据此推断延迟分位数或稳定加速比例。测试期间未并行运行项目测试。

原始报告：[修改前](search-cache-before-mc-1.6.0.json)、[修改后](search-cache-after-mc-1.6.0.json)。报告记录机器、Node、引擎、环境、语料、模型及关键源码 SHA256。两份报告的 Git HEAD 相同，未提交的实现差异由源码 SHA256 区分；评分规则未变，因此算法版本保持 `mc-1.6.0`。

## 实测结果

| 来源类别 | 首次请求：修改前 → 修改后 | 重复请求：修改前 → 修改后 | 每次选出评价调用：修改前 → 修改后 |
|---|---:|---:|---:|
| 灭歌 | 7.260 → 6.548 秒 | 3.922 → 3.485 秒 | 14,061 → 11,573 |
| 复活 | 11.592 → 12.497 秒 | 9.370 → 8.110 秒 | 33,475 → 29,355 |
| 空间 | 9.838 → 9.914 秒 | 5.943 → 5.414 秒 | 20,234 → 19,190 |
| 轻装 | 10.734 → 10.137 秒 | 8.306 → 7.091 秒 | 28,207 → 24,343 |
| 晴天 | 14.064 → 12.945 秒 | 8.331 → 7.271 秒 | 26,118 → 22,567 |
| 抛下狠话 | 7.848 → 10.534 秒 | 5.663 → 5.400 秒 | 21,263 → 19,033 |

12 组调用总数从 286,716 降至 252,122，减少约 12.1%；总耗时减少约 3.4%。重复请求均加速，首次请求有三组变慢。本次测量不能确定这些耗时波动的原因。

12 组全部完成四层补齐，每组返回四支合法队伍，原两位成员保持不变。修改前后有序配置、字段锁、指标、搜索状态计数、解释、来源以及按成员位置规范化的选出/Mega 引用哈希全部一致。随机 ID 和耗时不参与等价比较。

所有修改后用例仍超过三秒，**完整构筑三秒目标仍未通过**。本次没有重跑显式 3000 ms 预算实验，不替换历史的限时成队率；开发样本的输出等价也不能证明独立实战效果。

## 复现与检查

在仓库根目录执行：

```sh
pnpm benchmark:search --output=.local/search-cache-current.json --compare=docs/reports/search-cache-before-mc-1.6.0.json
pnpm verify
```

基准使用随包数据，无需相邻参考仓库或联网。对照时校验输入版本、来源、配置、预算和规范化输出；不一致会抛出断言。默认输出为 `.local/search-benchmark.json`，保留已有报告。

修改前报告由同一基准脚本在原 `search.ts` 上生成。重建该基线时，可在独立工作副本使用报告中的 Git 修订及当前基准脚本，核对报告列出的源码哈希后执行 `pnpm exec tsx tools/search-benchmark.ts --output=.local/search-before.json`。

本次 `pnpm verify` 通过类型检查及 11 个测试文件的 77 项测试。新增回归检查核心成员保持、选出引用、重复请求输出一致与标识独立，以及取消物种/道具重复限制后的六位成员标识唯一性。未重新执行桌面、打包或多小时持续运行验收。
